# 05 · 复盘：最难的问题、学习与下一步

## 1. 最难的问题：怎么证明"这是决策，不是流程"

题目有一句话把评分标准说穿了：

> 高分依据是合理重规划；无状态、无失败处理只能证明完成串行调用。

我第一版就是"串行调用"：`检索 → 估算 → 超了就换便宜的 → 生成 → 保存`。它跑得通、测试也绿，
但它和 `if budget < 12: plan = lean` 没有区别。真正让我意识到问题的是自己写验收用例时的这句：

```python
assert estimates[0][1] == "plan-standard"   # 先估贵的
assert estimates[1][1] == "plan-lean"       # 才换便宜的
```

要满足它，Agent 必须**先拿到 12 这个数字**，再决定换。也就是说，决策的输入必须是**上一步的返回值**，
而不是输入的档位。改完之后，同一个循环在预算 15 时完全不重规划——这条对照实验比任何文档都有说服力。

第二个坑是"重规划时复用任务 id"。表面上计划变了，但因为循环保留 done 状态，新任务直接被当成已完成跳过，
trace 看着完整、实际什么都没跑。这类 bug 只有把"中间状态"也断言出来才能抓到。

**结论**：判断一个 Agent 项目是不是"真 ReAct"，看它的 trace 里有没有一个**只能由观测结果解释**的动作。
如果没有，那就是披着 Agent 外衣的 pipeline。

## 2. 第二难：失败要"可注入"，不能"可祈祷"

一开始我想等真实模型偶尔失败来演示工具失败，这不可复现。改成 `fail_on={"draft_script": [1, 2]}`
之后，失败变成测试的一部分：第几次调用、哪个工具、返回什么错误码，全部确定。
Mock 和真实模型走同一套失败注入，所以两边都能演示"失败后怎么办"。

顺带发现一个设计点：失败任务不能从计划里删掉。删了，trace 里就只剩"一切顺利"，
评审无法核对。所以旧任务保留并标 `blocked` / `skipped`，`attempts` 和错误码都留着。

## 3. 第三难：预算到底包不包工具费

题目参考实例是"预算 10、初始 12、改 8、保存"，按这个读法预算只管方案成本。
但"工具调用也要花钱"在真实业务里同样成立，两种口径都说得通。

我的处理是**都实现、都打印、都写文档**：默认口径与题目一致，另一个口径一个开关切换。
这件事让我意识到，需求歧义不该偷偷选一个，而应该把选择摆到台面上——评审能自己核对，比我说"我对了"有用。

## 4. 学到了什么

1. **约束要放在代码里，不要放在 prompt 里。** prompt 是建议，代码是事实。模型可以无视规则，
   但它改不了 `save_plan` 里的预算校验，也绕不过 `max_turns`。
2. **让模型犯错，然后证明系统接住了。** `missing-budget-model` 里模型提交了非法依赖的计划，
   循环用 `INVALID_PLAN` 拒绝、模型下一轮自己修好——这比"模型一次做对"更能证明工程有效性。
3. **可复现性是一等公民。** 确定性 Mock + 失败注入 + 固定场景，让"同一输入两次结果一致"成为测试而不是口号。
4. **文档里的每个数字都要能跑出来。** 我删掉了 AI 初稿里所有没实跑过的描述（多 Agent、Web 界面），
   现在 README 里的每条命令我都实际执行过。
5. **Windows 沙箱的坑**：受限令牌下 `mkdtemp(mode=0700)` 建出的目录自己都写不进去，
   pytest 的 `tmp_path` 直接崩。用 `Path.mkdir()` 重建 fixture 解决，写进了 `tests/conftest.py` 的注释。

## 5. 如果继续做（按优先级）

| 优先级 | 事项 | 为什么 |
|---|---|---|
| P0 | 把 `MockPolicy` 的决策表换成"可配置策略"，用参数化测试扫预算/截止的边界 | 现在只测了几个离散场景，边界（如 7.9 单位）没覆盖 |
| P0 | 模型轨迹加"同场景多模型对比"（DeepSeek / GLM / Kimi），看决策差异 | 更能说明"框架不重要，约束和观测才重要" |
| P1 | 支持"部分成功"的细粒度续跑：只重跑失败的那一篇脚本，而不是整个 draft 任务 | 现在 draft 是整体成功/失败 |
| P1 | 把工具换成真实 HTTP 服务（带真实延迟与超时），验证超时路径 | 现在延迟是模拟的 |
| P2 | 多轮对话：运营看到方案后说"预算可以加 3 单位"，Agent 从 checkpoint 继续 | 更接近真实协作 |
| P2 | 成本预算的第三种口径：按时间窗口切分预算 | 长周期活动真实需要 |

## 6. 一句话总结

这个项目的价值不在于"能生成一份方案"，而在于**它会在钱不够、工具坏了的时候做出可解释的选择，
并且把"没做到"如实写出来**。评审要看的正是这个。
